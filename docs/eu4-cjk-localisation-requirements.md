## 1. 背景

EU4 的 Clausewitz 引擎（2013 年）原生不支持 CJK 字符显示。中文/日文社区通过
**双字节补丁 EU4dll**（DLL 注入 + hook 文本渲染路径 + 替换含 CJK 字形的字体）使游戏可以
显示双字节字符。但引擎自身的文本管线仍按类 Latin-1/CP1252 的单字节方式处理本地化文本，
UTF-8 多字节序列会被拆散破坏。因此本地化文件在进入游戏前必须经过一种特殊的**转码
（escape）**：把每个 CJK 字符展开为一串"引擎安全"的字节序列，DLL 渲染时再还原为 UCS-2
码点查字体。

这种转码后的文件对人类完全不可读（在 UTF-8/GBK 等任何常见编码下都显示为乱码）。目前
中文模组作者普遍依赖 ParaTranz 网站上的在线转换器在两套文件之间手工来回转换。

## 2. 问题陈述

以 EDG-KTP 模组为例，本地化目录中同时维护两套内容相同的文件：

- `localisation/l_english/*.yml` — UTF-8 BOM，人类可读中文（**母本**）；
- `localisation/replace/*.yml` — 转码后文件（**发行本**），游戏实际读取。

当前工作流的痛点：

1. **依赖外部网站**：每次改中文都要打开 paratranz.cn 在线转换、上传、下载、放回目录，
   流程割裂且无法离线/批量/自动化。
2. **双向都需要**：接收他人（或翻译平台产出）的转码文件后，同样要经网站转回可读版本
   才能审校。
3. **不同步风险**：改了母本忘记重新转码，或改了发行本忘记回写母本，两套文件悄悄漂移，
   表现为游戏内乱码/丢字/显示旧文案，且难以定位。
4. **工具链盲区**：git diff、grep、LSP（本仓库 ParadoxCode）等所有工具看到的都是乱码，
   无法对中文内容做检索、诊断和校对。

## 3. 现状调研（已完成）

### 3.1 双字节补丁如何工作

EU4dll 以 d3d9 代理 DLL 注入游戏，hook 本地化加载与文本渲染路径（`Plugin64/` 下的
`localization.cpp`、`font.cpp`、`c_bitmap_font.cpp` 等），并替换字体。转码核心位于
`Plugin64/escape_tool.cpp`（MIT 许可），关键函数：

- `convertWideTextToEscapedText`（UCS-2 → 转义字节流，游戏渲染前方向）
- `convertEscapedTextToWideText`（转义字节流 → UCS-2，反方向）

### 3.2 转码格式规格（逆向 + 实证还原）

> 结论先行：**该转码是纯算术规则，不需要任何码表。** 全部常量已从源码提取，并经样例
> 工程两份文件全量对拍验证（见 3.3）。

#### 3.2.1 常量

- **CP1252 特殊映射**（27 项，`0x80`–`0x9F` 区）：
  `U+20AC→0x80, U+201A→0x82, U+0192→0x83, U+201E→0x84, U+2026→0x85, U+2020→0x86,
  U+2021→0x87, U+02C6→0x88, U+2030→0x89, U+0160→0x8A, U+2039→0x8B, U+0152→0x8C,
  U+017D→0x8E, U+2018→0x91, U+2019→0x92, U+201C→0x93, U+201D→0x94, U+2022→0x95,
  U+2013→0x96, U+2014→0x97, U+02DC→0x98, U+2122→0x99, U+0161→0x9A, U+203A→0x9B,
  U+0153→0x9C, U+017E→0x9E, U+0178→0x9F`
- **转义字节集（EU4 规范档，23 项，高低字节分别判断；2026-09-11 经 paratranz 官方参考
  实现全量标定，见设计文档）**：
  `{0x00, 0x0A, 0x0D, 0x20, 0x22, 0x23, 0x24, 0x2F, 0x3B, 0x3D, 0x40, 0x5B, 0x5C,
  0x5D, 0x5F, 0x7B, 0x7D, 0x7E, 0x80, 0xA3, 0xA4, 0xA7, 0xBD}`
  （即 NUL、换行、空格、`"#$/:;<=>?@[\]_{|}~` 中的一部分及 `£¤§½` —— 引擎文本语法/
  路径/字体管线中有特殊含义的字节。EU4dll `escape_tool.cpp` 使用 29 值超集，paratranz
  线上内联转换器为 22 值变体，三者仅 `!`/`#`/`/` 等个别字节分歧，解码全部兼容）
- **偏移量**：marker `0x11/0x13` 时 `low += 0x0E`；marker `0x12/0x13` 时 `high -= 0x09`
- **PUA 平移**：`0x100 < cp < 0xA00` 的码点（拉丁扩展/希腊/西里尔等）编码前 `cp += 0xE000`
  （移入私用区，配套字体在平移后的码位上提供字形）

#### 3.2.2 编码（可读 → 转码），逐 UTF-16 码元 `c`

```
1. 若 c ∈ CP1252 映射的 27 个 Unicode 字符（如 U+2018 '）：
     输出单字节 b = 反查(c)，结束。
2. cp = c；若 0x100 < cp < 0xA00：cp += 0xE000
3. high = cp >> 8，low = cp & 0xFF
4. 若 high == 0：输出单字节 low，结束。
5. esc = 0x10；high ∈ 转义集 → esc += 2；low ∈ 转义集 → esc += 1
6. esc ∈ {0x11, 0x13} → low = (low + 0x0E) & 0xFF
   esc ∈ {0x12, 0x13} → high = (high - 0x09) & 0xFF
7. 依序输出字节：esc, low, high     ← 注意是 low 在前、high 在后
```

**落盘**：转码产物是字节流，文件按 UTF-8 BOM 写出时，每个字节 `b` 转为
`b < 0x80 → U+00xx`；`b` 命中 CP1252 映射 → 对应 Unicode 字符（如 `0x8A → U+0160 Š`）；
`b ∈ {0x81, 0x8D, 0x8F, 0x90, 0x9D}`（CP1252 未定义）→ C1 控制符直通（如 `0x8F → U+008F`）。

#### 3.2.3 解码（转码 → 可读），逐码点扫描

```
遇到 U+0010..U+0013（marker）：
    读后续两个码点，各自经 CP1252 反映射还原为字节 low、high（顺序 low 在前）
    sp = (high << 8) | low
    marker 0x11 → sp -= 0x0E；0x12 → sp += 0x900；0x13 → sp += 0x8F2
    若 0xE101 ≤ sp ≤ 0xE9FF → sp -= 0xE000   （PUA 平移还原）
    输出 sp
其他码点：原样输出
```

#### 3.2.4 文件级不变量

转码**只作用于文本字符流**，其余逐字节保留：

- UTF-8 BOM、CRLF 行尾、键名、冒号/引号/缩进、空行、`#` 注释全部不变；
- 本地化命令原样保留：`§Y`/`§!` 颜色码、`$VAR$`、`@KTP` 图标、`[Root.GetName]` 等
  （它们本身是 ASCII/单字节，落在转码直通路径上）；
- 条目顺序与键集合不变，文件间可按键一一对应。

#### 3.2.5 已知限制

- **BMP 限定**：算法按 UCS-2 码元处理。U+10000 以上字符（扩展 B 区生僻汉字、emoji）
  在文件层面以代理对形式往返，但发行字体无对应字形，游戏内显示豆腐块 → 一律视为
  不支持并给出诊断。
- `0x100–0x0A00` 区字符经 PUA 平移后依赖配套字体，不属于中文模组常规用字，仅需保底
  往返。

### 3.3 算法验证记录（2026-09-11）

依据 `escape_tool.cpp`（develop 分支）实现原型，对 EDG-KTP 的两份文件全量对拍：

| 检验 | 结果 |
|---|---|
| `decode(发行本) == 母本` | ✅ 完全一致 |
| `encode(母本) == 发行本` | ✅ 逐字节一致（转义集校准后） |
| `decode(encode(母本)) == 母本` | ✅ 往返无损 |

**关键发现 —— 三套转义集合并存，解码全部兼容（2026-09-11 完成全量标定，详见设计文档
`eu4-cjk-localisation-design.md`）：**

- 权威证据链：`matanki-saito/EU4SpecialEscape`（C++ 规范源）→ paratranz 官方 Gist
  `special-escape.js`（参考实现）→ 服务器文件转换器（产出用户文件）→ 线上内联转换器
  （部署版，存在 `0x21`/`0x23` 分歧）→ EU4dll DLL（29 值超集，游戏内解码）；
- **最终标定：EU4 规范档（Gist EU4 模式，23 值集合）encode(母本) == 发行本，逐字符一致**；
- 线上部署版 decode(发行本) == 母本（解码方向与集合无关，marker 自描述）；
- 部署版内联 encode 与规范档在 512 个字节位置中仅 6 处分歧（`!`/`#`/`/` × 高低位）。

字符级验证样例（节选，全部与文件实测吻合）：

| 字符 | 码点 | 高/低字节 | 转码三元组 | 磁盘 UTF-8 字节 |
|---|---|---|---|---|
| 同 | U+540C | 54 / 0C | `10 0C 54` | `10 0C 54` |
| 床 | U+5E8A | 5E / 8A | `10 8A 5E` | `10 C5A0 5E`（0x8A→Š） |
| 异 | U+5F02 | 5F / 02 | `12 02 56`（high 0x5F∈集，-9） | `12 02 56` |
| 圣 | U+5723 | 57 / 23 | `11 31 57`（low 0x23∈集，+14） | `11 31 57` |
| 级 | U+7EA7 | 7E / A7 | `13 B5 75`（双转义） | `13 B5 75` |
| 」 | U+300D | 30 / 0D | `11 1B 30`（low 0x0D∈集） | `11 1B 30` |
| 返 | U+8FD4 | 8F / D4 | `10 D4 8F` | `10 C394 C28F`（0x8F 为 CP1252 未定义→C1 直通） |
| 为 | U+4E3A | 4E / 3A | `10 3A 4E`（paratranz 不转义 0x3A） | `10 3A 4E` |

### 3.4 现有工作流与替代品

| 工具 | 能力 | 不足 |
|---|---|---|
| ParaTranz 在线转换器 | 双向转码，事实标准 | 仅在线、单次手工操作、无校验/无 CI、无 LSP 集成 |
| EU4dll 源码中的算法 | 规范来源 | 是游戏内 C++ 代码，非文件转换工具 |
| （本仓库现状） | localisation 解析、BOM 保留、Win-1252 回退 | 对转码格式一无所知，打开发行本即乱码 |

### 3.5 脚本内嵌形态（2026-09-11 增补）

转码文本同样出现在**非 yml 的游戏脚本**中（如 `history/countries/*.txt` 的人名/王朝名），
为**原始单字节**形态（无 BOM、CP1252/Latin-1 字节流、marker 与高低字节直接落盘，无
UTF-8 重编码），对应 paratranz 的 `Latin1（EU4 txt）` 目标档。paratranz 网页文本框因
剪贴板/编码误读破坏控制字节而无法处理此形态，仅文件上传通道可行——进一步印证需要
文件级 codec。完整规格、310 文件实测标定与方案见设计文档 §1.1/§2/§3.1。

## 4. 术语

| 术语 | 定义 |
|---|---|
| 母本（readable/source） | UTF-8 BOM、人类可读的本地化文件 |
| 发行本（escaped/gamed） | 转码后、游戏可读取的本地化文件 |
| 转码（transcode/escape） | §3.2 定义的字符流变换，双向、无损、纯算术 |
| marker | 转义三元组首字节 `0x10`–`0x13`，标记 CJK 序列并编码补偿方式 |
| 转义集（escape profile） | 决定何时升级 marker 的字节集合；含 `paratranz`（兼容默认）与 `dll-full`（最保守）两档 |
| 双字节补丁 | EU4dll，使游戏渲染 CJK 的 DLL 注入补丁 |

## 5. 用户与场景

- **模组作者（本人/核心用户）**：日常用编辑器改中文文案，希望"改完即生效"，不再访问
  在线转换器。
- **翻译协作者**：经 ParaTranz 平台产出/消费转码文件，需要与平台字节级兼容。
- **工具链/CI**：发布脚本中批量转码、校验，防止漏转码的文件进入发行包。

用户故事：

1. 作为模组作者，我编辑母本并保存后，工具自动（或一键）产出最新发行本，全程离线。
2. 作为模组作者，我拿到一份转码文件时，能立刻看到其中的中文内容（预览/转换），而不是
   乱码。
3. 作为模组作者，当我忘记转码、或两套文件内容漂移时，工具能在编辑器/CLI 中明确告诉我
   哪个键、哪一行不一致。
4. 作为发布者，我能在 CI 里跑一条命令完成全模组转码 + 校验，失败即阻断发布。
5. 作为翻译协作者，我经手 paratranz 的文件与本地工具产出的文件互认，diff 干净。

## 6. 目标与非目标

**目标**

1. 在 ParadoxCode 内提供完整、离线、双向的 EU4 中文本地化转码能力（Rust 核心 + CLI）。
2. 让编辑器（经 LSP）对发行本文件提供可读视图与一致性诊断，把"乱码不可维护"变成
   "透明可维护"。
3. 与 paratranz 输出字节级兼容（默认档），与 EU4dll 解码语义严格兼容。

**非目标**

1. 不做游戏内改动（补丁本身的安装、字体管理、IME 等）。
2. 不做 ParaTranz 平台的 API 集成/账号打通。
3. 一期不做"完全透明的虚拟文件系统编辑"（见 FR-5，远期）。
4. 不处理 CSV 本地化格式（与仓库现有边界一致）。
5. 不支持日文假名习惯与多语言变体码表（YAGNI；算法本身码点无关，天然可扩展）。

## 7. 功能需求

| # | 优先级 | 需求 |
|---|---|---|
| FR-1 | P0 | **编解码核心库**：按 §3.2 规格实现双向转码，纯函数、无状态、纯 Rust（建议落位 `pdx-parser` 或新 crate）。API 返回结构化结果（成功/不可编码码点列表），不 panic。支持 `paratranz` 与 `dll-full` 两档转义集。 |
| FR-2 | P0 | **CLI 转码与校验**：`pdx loc`（命名待定）子命令：单文件/目录双向转码、`--check` 只校验不写、`--dry-run`、`--profile`、目录映射（母本树 ↔ 发行本树，如 `l_english/ ↔ replace/`）。退出码供 CI 使用。保留 BOM/CRLF/结构（§3.2.4）。 |
| FR-3 | P1 | **一致性诊断**：a) 母本 vs `decode(发行本)` 的行/键级差异报告（漂移检测）；b) "可读中文被误存入发行本"检测（发行本中出现未转义 CJK 即告警）；c) 不可编码码点（非 BMP 等）警告。CLI 与 LSP 双入口，诊断码纳入 `docs/diagnostics.md` 体系。 |
| FR-4 | P1 | **编辑器可读性**：打开发行本时提供"解码预览"（命令输出/hover）；转义三元组的 inline 预览（复用 inlay hint 基建）；语义高亮把三元组作为整体着色。 |
| FR-5 | P2（可行性已确认，机制见 §9-B） | **透明编辑视图**：自定义 scheme（如 `pdxloc://`）注册 `FileSystemProvider`：`readFile` 读盘→解码→返回可读 UTF-8，`writeFile` 收到可读文本→编码→写回磁盘。编辑器内打开发行本直接看到中文，Ctrl+S 落盘即游戏编码。LSP 侧这些文档走 textSync（didOpen/didChange 传解码后全文），服务端不读盘，从根上绕开坐标映射；未打开文件的服务端文件操作经 URI 重写层解码访问。需配套：外部磁盘变更 watcher 映射、双重转码检测、状态栏指示当前视图。 |
| FR-7 | P2 | **git 集成**：clean/smudge filter（工作区保持转码、仓库 blob 存可读中文）+ textconv（diff 可读）+ 自动生成 `.gitattributes` 片段。依赖 FR-2 CLI 作为 filter 驱动程序。解决 O2（发行本入 git 的 diff 噪音）并使 `git diff/log/blame` 全部可读。注意：VS Code SCM 视图的 diff 是否吃 textconv 需实现期验证，命令行 git 确定可读。 |
| FR-6 | P1 | **兼容性测试基建**：黄金语料 = EDG-KTP 文件对 + 全量探针（每个转义集字节值 × 高/低位置 × 常用汉字抽样）+ paratranz 对拍样例；纳入 CI 与 fuzz（仓库已有 `parse_localisation` fuzz 先例）。用于把 §3.3 的转义集结论从"样例验证"升级为"全量标定"。 |
| FR-8 | P1 | **本地化数据库单源化**（机制见方案文档 §7）：预览/hover/补全消费的本地化值改为每 (键, 语言) 恰一有效值。层序 current mod > dependency（按声明序）> vanilla；同层内一律平等（不区分 `l_*` 与 `replace/`），按读取序后来居上。值经 FR-1 解码器在引擎读取处（分类器门控）取自发行本真实文本，消灭"两套本地化并存"的多值与乱码。配套：索引缓存携带 codec 版本号、跳转定义坐标映射。 |

## 8. 非功能需求

- **正确性**：BMP 内任意字符往返无损（性质测试）；`encode` 幂等于已转码文件则报错或
  拒绝（防双重转码）。
- **性能**：MB 级本地化树毫秒级完成，支持万条目文件。
- **可移植**：纯 Rust 核心，不依赖 Win32 API（DLL 源码用 `MultiByteToWideChar`，我们
  用等价的 UTF-8↔UTF-16 语义即可）。
- **可观测**：所有差异报告定位到 文件:行:列。
- **许可**：EU4dll 为 MIT，算法思想自由实现；文档中注明规范来源。

## 9. 方案空间与推荐路线

| 方案 | 思路 | 优点 | 缺点 |
|---|---|---|---|
| **A. 双文件 + 构建同步**（推荐一期） | 母本为唯一编辑入口，CLI/保存钩子生成发行本 | 简单可靠；git 里中文可读；离线；CI 友善 | 磁盘仍两份；直接打开发行本仍是乱码（FR-4 缓解） |
| **B. 单文件 + 编辑器透明视图**（推荐三期，可行性已确认） | 自定义 scheme 的 `FileSystemProvider`：读时解码、存时编码，编辑器内完全透明 | 零同步问题、体验最佳；位置映射可经 LSP textSync 绕开（FR-5）；有 vscode-remote-repositories 等成熟先例 | VS Code 无法注册原生编码（`files.encoding` 无扩展点），必须走虚拟 scheme；外部工具（grep、其他编辑器）仍见转码字节——由 FR-7 git filter 补齐 |
| **C. 独立小工具**（不单独立项） | 单 exe watcher | 最快见效 | 与 ParadoxCode 生态割裂；其能力被 FR-1/FR-2 自然覆盖 |
| **D. 维持 paratranz 在线流程** | 现状 | 无开发量 | 不解决任何痛点（见 §2） |

**推荐路线**：Phase 1 = FR-1 + FR-2（codec 与 CLI，立即可用）；Phase 2 = FR-3 + FR-6
（诊断与标定）；Phase 3 = FR-4；远期评估 FR-5。

## 10. 约束与风险

| # | 风险 | 缓解 |
|---|---|---|
| R1 | paratranz 转义集未经全量标定（`0x3A/0x2A` 仅在 low 位置证伪；其余成员无反例但未全覆盖） | FR-6 探针语料 + `--profile` 双档，默认 paratranz 档遇未知场景可切 `dll-full`（功能始终正确） |
| R2 | EU4dll 版本差异：本规格取自 develop（1.37.5.0）；master 支持 1.34.2，算法可能不同 | 对拍两个分支的 `escape_tool.cpp`；文档记录版本对应 |
| R3 | 母本放在 `localisation/` 下会被游戏一并加载（`replace/` 优先级更高，通常无害，但删除键时可能残留旧文案） | 目录映射配置支持把母本放 `localisation/` 之外（如 `localisation_src/`）；开放问题 O1 |
| R4 | 非 BMP 字符文件层可往返但游戏无字形 | FR-3c 诊断 + 文档明示 BMP 边界 |
| R5 | DLL 源码 `convertWideTextToEscapedText` 的 CP1252 早退分支写 `(BYTE)cp`，疑似 bug | 我们的编码按正确语义（输出 CP1252 字节）并用黄金语料锁定行为 |
| R6 | 双重转码（对发行本再 encode）造成不可逆损坏 | encode 前检测输入含 marker 序列即拒绝（NFR） |

## 11. 开放问题（需决策）

- **O1 母本目录约定**：留在 `localisation/l_english/`（现状，游戏会加载）还是移出
  `localisation/`（更干净，但改变现有布局）？
- **O2 发行本是否入 git**：入（发布即用，但 diff 噪音）vs 不入（构建产物，需发布流程
  保证生成）。
- **O3 CLI 命令形态**：`pdx loc transcode|check` 还是并入现有 `pdx check` 体系？
- **O4 目录映射配置**：放 `pdx` 项目配置、`.mod` 文件旁的约定，还是 CLI 参数？
- **O5 字节级兼容承诺范围**：仅默认 paratranz 档，还是提供 `--exact-paratranz` 严格模式
  （探针标定完成前无法承诺 100%）？
- **O6 透明视图的产品形态**：虚拟 scheme 文件夹加入工作区（全量透明）vs 命令逐文件打开
  vs 先做只读解码预览（`TextDocumentContentProvider`，工作量最小）；扩展内 codec 用
  Rust→WASM 单一实现还是 TS 移植 + 共享黄金语料。

## 12. 验收标准

1. EDG-KTP 文件对：`encode(母本) == 发行本`、`decode(发行本) == 母本`，逐字节
   （探针脚本已达成，需转化为仓库内回归测试）。
2. 探针语料（覆盖全部转义集字节 × 高/低位置）往返无损，无逃逸错误。
3. `--check` 能捕获三类真实事故：忘转码、半转码（混合状态）、两套文件键/值漂移。
4. 用工具生成的发行本进游戏实测显示正常（最终人工验收）。
5. 文档：算法规格（本文 §3.2）进入正式文档；诊断码进 `docs/diagnostics.md`。
